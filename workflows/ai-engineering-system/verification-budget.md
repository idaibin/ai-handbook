# Verification Budget

- **Status:** candidate
- **Applies at:** 修改完成后、执行验证前
- **Purpose:** 用最小充分证据验证当前主张，避免无条件完整构建，也避免以“改动很小”为由跳过必要验证。

## 1. 触发方式

下游仓库的 `AGENTS.md` 只需要保存一条路由，不复制本文件：

> 修改完成进入验证阶段时，读取 ai-handbook 的 `workflows/ai-engineering-system/verification-budget.md`，选择最小充分验证；满足升级条件前不得默认运行完整构建。

执行者必须先写清本次需要证明的主张，再选择验证层级。验证预算由影响边界、失败风险和主张决定，不由改动行数单独决定。

## 2. 最小充分验证

| 层级 | 适用情况 | 最小证据示例 |
| --- | --- | --- |
| V0 静态 | 文档、注释、文案、局部非行为配置 | diff、语法/格式检查、链接或 schema 检查 |
| V1 定向 | 单一函数、模块、组件或包内行为 | 相关单测、目标 lint、目标 typecheck |
| V2 受影响构建 | 公共类型、入口、依赖、构建配置、生成物或跨模块契约 | 受影响包/应用的构建与测试 |
| V3 运行时/集成 | API、数据库、认证、文件系统、网络、权限、外部服务 | 目标运行时实验或集成测试 |
| V4 浏览器/E2E | 用户交互、布局、视觉结果、路由、浏览器专有行为 | 定向浏览器流程、截图或 E2E |

从能够证伪当前主张的最低层开始。一旦证据足够即停止，不为“更放心”自动叠加更高层验证。

## 3. 升级条件

仅在以下任一条件成立时升级：

- 当前检查失败，且更高层能定位或排除失败；
- 静态影响范围不确定，涉及共享契约、入口、生成物或多个包；
- 改动触达构建配置、依赖锁文件、编译器配置或工作区根配置；
- 主张本身是“可构建”“可运行”“集成正常”或“浏览器中正确”；
- 存在历史回归案例，且对应层级有明确检查；
- 用户、CI 或仓库政策明确要求。

完整仓库构建只在根级配置/依赖变化、跨项目契约变化、受影响范围无法可靠收窄，或明确要求时执行。

## 4. 常见选择

- 文案、注释、Markdown 小改：V0；不完整构建。
- 局部样式值变化：V0；若需要证明视觉结果，再加定向 V4；不默认完整构建。
- 单个纯函数逻辑变化：V1，运行相关测试。
- 公共类型或导出变化：V2，构建/测试受影响包。
- API、数据库或权限行为变化：V3。
- 点击、路由、响应式布局或浏览器兼容问题：V4。
- 根依赖、构建工具、工作区配置变化：V2，必要时完整仓库构建。

## 5. 验证记录

交付时至少记录：

- 需要证明的主张；
- 选择的层级和命令/检查；
- 结果；
- 未执行的更高层验证及原因；
- 剩余风险或环境缺口。

不能把 V0/V1 结果表述为已证明运行时、浏览器或生产行为。

## 6. 反馈与回归

本规则的触发反例是：局部小改在没有构建边界风险时仍默认执行完整构建，造成不必要的时间和算力成本。

若最小验证漏掉真实回归，应记录：

1. 漏掉的故障；
2. 当时的主张和所选层级；
3. 能够提前捕获故障的最低层检查；
4. 新增的 Evaluation；
5. 是否需要调整升级条件。

本文件在真实任务试运行和独立 Review 完成前保持 candidate，不能由提出者自行晋级为 active。
