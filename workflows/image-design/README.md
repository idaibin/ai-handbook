# 图片驱动的 UI 设计与实现流程

- **Version:** `0.1.0`
- **Status:** active workflow; cross-project effectiveness not yet validated
- **Canonical owner:** `idaibin/ai-handbook`
- **Applies to:** 需要外部生图、视觉方向探索和前端实现闭环的产品 UI 任务

本流程维护“本地规范 → 生图 → 审查 → 实现 → 浏览器验收”的唯一治理路径。它不规定某种固定视觉风格，也不把生成图、构建通过或静态截图当成运行完成。

知识依据位于 `knowledge-distillation/examples/engineering/image-first-ui-delivery/`。当前依据包含 Impeccable 的 Neo Mirai 第一方案例和 Garden Web Design Engineer 工作流；它们支持方法设计，不是跨项目效果证明。

## 1. 职责边界

| 对象 | 权威职责 |
| --- | --- |
| 本地 UI 规范 | 页面任务、真实内容、组件、状态、Token、视口、排除项和验收标准 |
| 完整生图提示词 | 当前规范在指定提供方上的一次性视觉任务 |
| 提供方原图 | 归属明确的原始视觉候选，保留原尺寸和哈希 |
| 本地衍生图 | 明确标注的缩放、补边或格式转换结果，不冒充原图 |
| 目标项目源码 | 可维护组件、交互、响应式行为和业务事实 |
| 浏览器证据 | 固定视口和真实状态下的最终可见行为 |

提供方会话不是唯一事实源。每次修改必须先进入本地 UI 规范和完整提示词，再允许下一次外部提交。

## 2. 七阶段流程

### Stage 1 — Freeze

在目标项目的本地任务目录中冻结：

- 页面与用户的单一主要任务；
- 组件库、现有组件与 Token；
- 真实字段、指标、操作和状态；
- 目标视口与缩放比例；
- 必须出现和禁止出现的元素；
- 交互、响应式和无障碍验收条件。

未冻结规范时，不进入生图。

### Stage 2 — Prompt

从本地规范生成一个完整提示词文件。提示词必须声明：

- 固定 basis 和目标提供方；
- 单图或多图合同；
- 原生画布尺寸；
- 信息层级和组件约束；
- 强负面约束；
- 单次提交、停止和失败处理。

聊天里的补充说明不能替代更新提示词文件。

### Stage 3 — Generate

只通过当前授权的提供方、项目和浏览器路线发送一次。发送前记录 prompt hash；发送后记录会话 ID、提交次数、完成状态和输出归属。

超时、浏览器断开或结果不明确时，只回查原会话。没有“提交前失败”的直接证据，不重发、不 regenerate、不换提供方制造结果。

### Stage 4 — Review

保存提供方原图并核对：

- 实际宽高、格式和 SHA-256；
- 构图、层级、密度和文字质量；
- 组件是否能映射到目标组件库；
- 是否虚构功能、数据或状态；
- 默认、加载、空、错误、权限和窄屏状态是否可推导；
- 是否满足原生目标画布。

若原图不是目标尺寸，保留原图；衍生图必须另命名并记录转换方法。放大后的 `1920×1080` 文件不等于原生 `1920×1080` 设计。

### Stage 5 — Decide

记录三类结论：

- `accepted`：进入本地 UI 规范的决定；
- `rejected`：明确不再出现的方向；
- `open`：需要下一轮验证的问题。

需要再生图时，先修改本地 UI 规范和完整提示词，生成新的版本和 operation ID，然后再提交。

### Stage 6 — Implement

按目标项目现有组件库实现。生成图只指导构图、层级、配色和资产方向；表单、表格、导航、抽屉、弹窗、反馈、焦点和响应式行为由项目现有组件和规则负责。

不得为了贴图而：

- 引入第二套组件库；
- 绘制假的系统控件；
- 绕过真实数据和权限状态；
- 用固定高度隐藏溢出；
- 把营销站的视觉结构套到后台系统。

### Stage 7 — Verify

至少分开记录：

1. UI 规范审查；
2. 源码与类型检查；
3. 构建与测试；
4. 固定视口浏览器截图；
5. 关键交互与状态；
6. 未验证的集成或生产边界。

只有运行页面完成验收后，才能把候选图对应的方向标记为已实现。

## 3. 最小产物结构

目标项目未批准的工作保存在其忽略目录，例如：

```text
.codex/reviews/<design-id>/
├── UI-SPEC.md
├── IMAGE-PROMPT.md
├── operation.md
├── provider-original.png
├── derivative-1920x1080.png
├── decision.md
└── browser-evidence/
```

批准后的稳定跨页面视觉语义进入目标项目的正式设计文档；原始会话、过程图和未接受方案不进入产品规范。

## 4. RustZen Admin 适配决策

当前 `rustzen-admin` 已使用 Ant Design 6、Ant Design Pro Components、`ProLayout`、`ProTable`、`ConfigProvider`，并由仓库根 `DESIGN.md` 约束共享视觉语义。因此：

1. **Impeccable 适合作为主流程参考**：用于读取现有产品、约束设计上下文、区分 product/brand、执行 critique/audit/polish/adapt/harden。
2. **Garden Web Design Engineer 适合作为设计输入**：用于冻结 Design Read、密度、视觉方向、Token 和验收条件；不直接把某个 style recipe 当成 RustZen 主题。
3. **Ant Design 6 / Pro Components 是实现权威**：组件、交互、状态、可访问性和主题必须映射回现有实现，优先级高于任何外部 Skill。
4. **UI/UX Pro Max 只作为查询资料库**：可查配色、字体、UX 和响应式规则，不作为自动生成整套设计系统的 owner。
5. **gstack 只借鉴验证循环**：可学习固定视口、修改前后截图和浏览器复核；不引入其自动提交或 Pretext 路径。

## 5. 维护规则

- 版本变化只修改本文件，不复制到 ChatGPT Project 指令或目标仓库。
- 新案例先登记来源、适用边界和证据状态，再改变流程。
- 单一项目成功只更新案例记录；至少两个异构项目出现可重复增益且无明显回归后，才评估晋级为生产 Skill。
- 每次失败必须归类为规范、提示词、提供方、图片审查、实现或浏览器验收问题，不能统一归因于“模型审美”。

## 6. 当前证据状态

- Neo Mirai：第一方案例，已查看其方向图、实现页面和案例说明；未独立复现完整执行链。
- Garden Web Design Engineer：固定仓库版本的公开工作流和案例；未在 RustZen 上完成对照实验。
- RustZen Admin：当前源码与 `DESIGN.md` 已核对 Ant Design/Pro Components 所有权；本流程尚未在完成后的 RustZen 页面上取得浏览器验收结果。

因此，本流程可以作为当前工作方法，但不能宣称已经提升 RustZen 的 UI 质量。
