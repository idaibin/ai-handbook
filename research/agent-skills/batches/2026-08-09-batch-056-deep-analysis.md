## Deep-analysis findings

### 1. Repository identity and content identity are different dimensions

The ten qualified GitHub repository identities collapse to only three exact Git trees and three exact `SKILL.md` blobs. The three content identities were already deep-analyzed in earlier batches, so this batch increases repository-identity coverage by ten but creates no duplicate individual Skill report. This is intentional: repository identity, content identity, and runtime-validation state must remain independently traceable.

### 2. Baseline `html-ppt` structure is strong, but hand-maintained inventory drifts

The `c9b2a942...` and `656ebee6...` snapshots use a useful progressive-disclosure structure: `SKILL.md` for routing/authoring rules, `references/` for themes/layouts/animations/full decks, `assets/` for the tokenized presentation runtime, `templates/` for reusable pages/decks, and `scripts/` for scaffolding/rendering. The Skill advertises 31 single-page layouts while still containing the stale instruction to add a layout only when none of the “30” fit. Inventory should therefore be generated or checked from the tree rather than trusted as manually synchronized prose.

### 3. Stored screenshots are artifacts, not reproduced validation

The `c9b2a942...` tree contains `scripts/verify-output/` PNG inventories for theme and animation showcases. Those files demonstrate that visual artifacts exist in the repository, but they do not establish that the pinned tree was rendered in this batch, that the images were generated by the current code, or that an assertion-based visual comparison passed. They remain source evidence only.

### 4. Rendering is macOS-specific and weakens browser isolation

Across all three unique content snapshots, `scripts/render.sh` is the same blob. It hard-codes `/Applications/Google Chrome.app/Contents/MacOS/Google Chrome`, explicitly assumes macOS, launches Chrome with `--no-sandbox`, and detects an “all” slide count by grepping the literal `class="slide"` pattern. The renderer is therefore not a portable cross-platform validation gate and may miscount slides when class serialization differs. Portable browser discovery/preflight plus deterministic visual assertions would be a stronger contract.

### 5. Presenter mode expands runtime state without an automated browser gate

The `c7a57a16...` presenter-mode variant adds a popup presenter window, CURRENT/NEXT previews, speaker-script/timer cards, `localStorage` layout persistence, `BroadcastChannel` synchronization, iframe `?preview=N`, and `postMessage` slide updates. The design keeps presenter and audience views on one runtime, which is preferable to separate rendering stacks. However, the tree contains no automated browser E2E/eval proving popup behavior, cross-window synchronization, persisted layout, preview equivalence, or no-flicker claims. The unchanged screenshot renderer cannot validate those presenter-specific behaviors.
